# Maglev 调试标志使用指南

本文档通过 4 个简单独立的用例，详细讲解 V8 Maglev 编译器的三个主要调试标志。

## 概述

### 测试用例

| 用例 | 文件                         | 功能                  | 重点                    |
| ---- | ---------------------------- | --------------------- | ----------------------- |
| 1    | `01_loop.js`                 | 简单循环求和          | 循环优化、循环剥离      |
| 2    | `02_if_else.js`              | if-else 条件分支      | 分支优化、控制流        |
| 3    | `03_try_catch.js`            | try-catch（不抛异常） | 异常处理、Handler Table |
| 4    | `04_try_catch_with_error.js` | try-catch（抛异常）   | 异常捕获路径            |

### 调试标志

| 标志                            | 功能               | 输出内容                        |
| ------------------------------- | ------------------ | ------------------------------- |
| `--print-maglev-graph`          | 打印最终优化后的图 | Block 结构、IR 节点、寄存器分配 |
| `--print-maglev-graphs`         | 打印所有优化阶段   | 每个优化 pass 的 IR 图          |
| `--trace-maglev-graph-building` | 跟踪图构建过程     | 字节码到 IR 的转换细节          |

## 一、BytecodeArray 结构详解

### 什么是 BytecodeArray？

BytecodeArray 是 V8 Ignition 解释器使用的字节码表示，Maglev 编译器将其作为输入进行优化编译。

### 用例 3: try-catch 的 BytecodeArray

```bash
out/x64.debug/d8 --allow-natives-syntax --print-bytecode v8_analyze/maglev_examples/03_try_catch.js
```

#### 完整输出

`--print-bytecode` 会打印**两个部分**的字节码：

1. **顶层代码**：整个脚本的执行代码（包括预热循环、函数调用等）
2. **safeDivide 函数**：函数本身的字节码（我们重点分析的部分）

**下面我们重点分析这部分**（safeDivide 函数）。

### BytecodeArray 组成部分

#### 1. 元数据

```
Bytecode length: 22       # 字节码总长度（字节）
Parameter count 3         # 参数数量：this + a + b = 3
Register count 2          # 寄存器数量：r0, r1
Frame size 16             # 栈帧大小：2个寄存器 × 8字节 = 16字节
```

**说明**：

- **Parameter count**: 包括隐式的 `this` 参数
- **Register count**: 局部寄存器（不是 CPU 寄存器，是字节码虚拟寄存器）
- **Frame size**: 栈帧中局部变量占用的空间

#### 2. 字节码指令

每条指令的格式：

```
地址 @ 偏移 : 操作码 操作数... 指令名 操作数...
```

**正常执行路径（偏移 0-8）**：

```
0x16c800800158 @  0 : 1b ff f9    Mov <context>, r0
```

- **操作码 `1b`**: Mov 指令
- **操作数 `ff f9`**: 将 context 移动到 r0
- **作用**: 保存上下文（用于闭包、try-catch 等）

```
0x16c80080015b @  3 : 0b 04       Ldar a1
```

- **操作码 `0b`**: Ldar（Load Accumulator from Register）
- **操作数 `04`**: 参数 a1（即参数 b）
- **作用**: 将 b 加载到累加器

```
0x16c80080015d @  5 : 43 03 00    Div a0, [0]
```

- **操作码 `43`**: Div（除法）
- **操作数 `03`**: 参数 a0（即参数 a）
- **操作数 `[0]`**: 反馈槽位索引
- **作用**: 计算 `a / b`（a0 / 累加器）

```
0x16c800800160 @  8 : b7          Return
```

- **操作码 `b7`**: Return
- **作用**: 返回累加器中的值

**异常处理路径（偏移 9-21）**：

```
0x16c800800161 @  9 : d1          Star1
```

- **操作码 `d1`**: Star1（Store Accumulator in Register 1）
- **作用**: 将异常对象存入 r1

```
0x16c800800162 @ 10 : 8d f8 00    CreateCatchContext r1, [0]
```

- **操作码 `8d`**: CreateCatchContext
- **操作数 `f8`**: r1（异常对象）
- **操作数 `[0]`**: 常量池索引（指向 CATCH_SCOPE）
- **作用**: 创建 catch 块的上下文

```
0x16c800800165 @ 13 : d2          Star0
```

- **作用**: 将新创建的 context 存入 r0

```
0x16c800800166 @ 14 : 10          LdaTheHole
```

- **操作码 `10`**: LdaTheHole
- **作用**: 将 `the_hole` 值加载到累加器（用于清除异常状态）

```
0x16c800800167 @ 15 : b4          SetPendingMessage
```

- **操作码 `b4`**: SetPendingMessage
- **作用**: 清除待处理的异常消息

```
0x16c800800168 @ 16 : 0b f9       Ldar r0
```

- **作用**: 加载新的 context

```
0x16c80080016a @ 18 : 1c f8       PushContext r1
```

- **操作码 `1c`**: PushContext
- **作用**: 将 context 推入上下文栈

```
0x16c80080016c @ 20 : 0c          LdaZero
```

- **操作码 `0c`**: LdaZero
- **作用**: 加载常量 0（catch 块返回 0）

```
0x16c80080016d @ 21 : b7          Return
```

- **作用**: 返回 0

#### 3. Constant Pool（常量池）

```
Constant pool (size = 1)
0x16c800800125: [TrustedFixedArray]
 - length: 1
           0: 0x2a650082cb5d <ScopeInfo CATCH_SCOPE>
```

**作用**：

- 索引 0：指向 CATCH_SCOPE 的 ScopeInfo
- CreateCatchContext 指令使用 `[0]` 访问此常量

**ScopeInfo 详细信息**：参见 [ScopeInfo 深度解析](./scope_info_deep_dive.md)

#### 4. Handler Table（异常处理表）

```
Handler Table (size = 16)
   from   to       hdlr (prediction,   data)
  (   3,   9)  ->     9 (prediction=1, data=0)
```

**含义**：

- **from-to 范围 [3, 9)**：字节码偏移 3-8 的指令在 try 块中
  - 偏移 3: `Ldar a1`
  - 偏移 5: `Div a0, [0]`
  - 偏移 8: `Return`
- **hdlr: 9**：如果抛出异常，跳转到偏移 9（catch 块开始）
- **prediction: 1**：预测不会抛异常（优化提示）
- **data: 0**：指向常量池索引 0（CATCH_SCOPE）

**工作流程**：

1. 执行偏移 3-8 的指令
2. 如果抛出异常 → 跳转到偏移 9（异常处理路径）
3. 如果没有异常 → 偏移 8 Return（正常路径）

**多个异常处理器的对应关系**：详见 [exception_handler_mapping.md](./exception_handler_mapping.md)

#### 5. Source Position Table

```
Source Position Table (size = 0)
```

**说明**：此表为空，因为没有启用源码位置映射。在生产环境或启用调试信息时，此表包含字节码偏移到 JavaScript 源码行号的映射。

### 控制流分析

```
正常执行：
0 → 3 → 5 → 8 (Return)

异常执行：
0 → 3 → 5 (抛异常) → 9 → 10 → 13 → 14 → 15 → 16 → 18 → 20 → 21 (Return)
```

### 与 JavaScript 源码对应

```javascript
function safeDivide(a, b) {
  // 偏移 0: Mov context
  try {
    // 偏移 3-8: 正常执行路径
    return a / b; // 偏移 5: Div, 偏移 8: Return
  } catch (e) {
    // 偏移 9-21: 异常处理路径
    return 0; // 偏移 20: LdaZero, 偏移 21: Return
  }
}
```

### 关键观察点

1. **try-catch 的开销**：

   - 正常路径：4 条指令（偏移 0, 3, 5, 8）
   - 异常路径：13 条指令（偏移 9-21）
   - Handler Table 需要额外的元数据

2. **优化机会**：

   - Maglev 可以内联正常路径
   - 异常路径通常不会被优化（冷路径）
   - Handler Table 在编译时可以静态分析

3. **性能影响**：
   - 如果不抛异常：开销很小（只有 Handler Table 查表）
   - 如果频繁抛异常：性能会显著下降

## 二、--print-maglev-graph：最终优化图

`--print-maglev-graph` 打印经过所有优化后的最终 Maglev IR 图，包含完整的 Block 结构和寄存器分配结果。

### 用例 1: 简单循环（loop）

#### 源码

```javascript
function simpleLoop(arr) {
  let sum = 0;
  for (let i = 0; i < arr.length; i++) {
    sum += arr[i];
  }
  return sum;
}
```

#### 执行命令

```bash
# 禁用 loop peeling 以简化控制流
out/x64.debug/d8 --allow-natives-syntax --no-maglev-loop-peeling --print-maglev-graph v8_analyze/maglev_examples/01_loop.js
```

#### Block 控制流图概览

```
b0（入口）
 ↓
b1（循环准备，加载 arr.length）
 ↓
b2（循环头）← ─────┐
 ├ phi 节点         │
 ├ CheckMaps        │
 ├ i < length?      │
 ├─ true → b3       │
 └─ false → b4      │
    ↓               │
   b3（循环体）     │
    ├ arr[i]        │
    ├ sum += arr[i] │
    ├ i++           │
    ├ ReduceInterrupt│
    └ 跳回 b2 ──────┘

   b4（退出）
    └ return sum
```

**关键 Block**：

- **b0**: 函数入口，FunctionEntryStackCheck
- **b1**: 循环准备，加载 `arr.length`
- **b2**: 循环头（phi 节点 + 循环条件判断 `i < length`）
- **b3**: 循环体（`arr[i]` + `sum += arr[i]` + `i++` + 跳回 b2）
- **b4**: 退出循环，返回 sum

#### Block 控制流图逐行分析

**执行命令（禁用 loop peeling）**：

```bash
out/x64.debug/d8 --allow-natives-syntax --no-maglev-loop-peeling --print-maglev-graph v8_analyze/maglev_examples/01_loop.js 2>&1
```

##### 编译时常量节点

在所有 Block 执行之前，Maglev 会创建一些**编译时常量节点**，这些节点存储在虚拟寄存器 `v-1` 中，表示它们不占用实际寄存器，而是嵌入到指令中。

**IR 常量定义**：

```
 1/27: Constant(0x002b0082cae9 <FeedbackCell[one closure]>) → v-1, live range: [1-25]
  2/3: Constant(0x002b0082cb21 <JSFunction simpleLoop (sfi = 0x2b0082ca4d)>) → v-1, live range: [2-23]
  3/4: Constant(0x002b0082cb09 <ScriptContext[4]>) → v-1, live range: [3-23]
 4/34: Int32Constant(0) → v-1, live range: [4-9]
```

**逐个分析**：

1. **1/27: Constant(FeedbackCell[one closure])**

   - **节点 ID**: 1（当前）/ 27（原始）
   - **类型**: FeedbackCell（反馈单元）
   - **用途**:
     - 存储函数的类型反馈信息
     - "one closure" 表示此函数只有一个闭包实例
     - 用于 ReduceInterruptBudgetForLoop 等需要访问反馈信息的操作
   - **Live range**: [1-25]（几乎整个函数生命周期）
   - **位置**: `→ v-1`（虚拟寄存器，编译时常量）

2. **2/3: Constant(JSFunction simpleLoop)**

   - **类型**: JSFunction（JavaScript 函数对象）
   - **SharedFunctionInfo**: 0x2b0082ca4d（共享函数信息）
   - **用途**:
     - 表示当前正在编译的函数本身
     - 用于函数调用、反优化时恢复上下文
   - **Live range**: [2-23]

3. **3/4: Constant(ScriptContext[4])**

   - **类型**: ScriptContext（脚本上下文）
   - **大小**: [4]（包含 4 个槽位）
   - **用途**:
     - 存储脚本级别的变量和声明
     - 包含全局作用域中的 `simpleLoop` 函数
     - 用于访问外部作用域的变量
   - **Live range**: [3-23]

4. **4/34: Int32Constant(0)**
   - **类型**: Int32Constant（32 位整数常量）
   - **值**: 0
   - **用途**:
     - 表示循环初始值 `let sum = 0` 的常量 0
     - 作为 phi 节点的初始输入（b1 → b2 的 sum 初始值）
   - **Live range**: [4-9]（仅在循环开始前使用）
   - **注意**: 这是 **int32 类型**，不是 Smi，因为 Maglev 已经将其解标记

**为什么使用 v-1（虚拟寄存器）？**

- 这些常量在编译时就已知，不需要在运行时计算
- 直接嵌入到指令的立即数（immediate）字段中
- 节省实际物理寄存器（rax、rbx 等）
- 提高代码密度和性能

**与 Block 中的节点区别**：

| 特性       | 编译时常量（v-1）                          | Block 中的节点               |
| ---------- | ------------------------------------------ | ---------------------------- |
| 创建时机   | 编译时                                     | 运行时                       |
| 寄存器分配 | 虚拟寄存器 v-1                             | 物理寄存器（rax, rbx 等）    |
| 值是否变化 | 不变                                       | 可能变化                     |
| 示例       | FeedbackCell, JSFunction, Int32Constant(0) | InitialValue, Phi, CheckMaps |

##### Block b0: 函数入口

**对应 BytecodeArray**：

```
  0 : LdaZero
```

**IR 指令**：

```
Block b0
0x002b0082ca4d <SharedFunctionInfo simpleLoop> (0x002b00848e59 <String[37]: "v8_analyze/maglev_examples/01_loop.js">:1:19)
  0 : LdaZero
   5/1: InitialValue(<this>) → [stack:-6|t], live range: [5-23]
   6/2: InitialValue(a0) → [stack:-7|t], live range: [6-23]
   7/6: FunctionEntryStackCheck
        ↳ lazy @-1 (3 live vars)
   8/7: Jump b1
```

**逐行解释**：

1. **源位置信息**：

   ```
   0x002b0082ca4d <SharedFunctionInfo simpleLoop> (0x002b00848e59 <String[37]: "v8_analyze/maglev_examples/01_loop.js">:1:19)
   ```

   - **SharedFunctionInfo 地址**: `0x002b0082ca4d`（函数元数据）
   - **函数名**: `simpleLoop`
   - **源文件**: `v8_analyze/maglev_examples/01_loop.js`
   - **源位置**: `1:19`（第 1 行第 19 列，即 `function simpleLoop(arr) {` 中的 `simpleLoop` 开始位置）
   - **用途**:
     - 调试时定位源代码
     - 反优化时恢复栈帧信息
     - 性能分析时关联源代码

2. **字节码 `0 : LdaZero`**：

   - Load Zero（加载常量 0）
   - 对应 JavaScript: `let sum = 0`

3. **`5/1: InitialValue(<this>)`**：

   - **节点 ID**：5（当前）/ 1（原始）
   - **操作**：初始化 `this` 参数
   - **位置**：`→ [stack:-6|t]`，存储在栈槽位 -6
   - **类型**：`t` = tagged（可能是任何 JavaScript 值）
   - **live range: [5-23]**：此值从指令 5 到 23 都存活

4. **`6/2: InitialValue(a0)`**：

   - **操作**：初始化参数 `a0`（即 `arr`）
   - **位置**：`→ [stack:-7|t]`，存储在栈槽位 -7

5. **`7/6: FunctionEntryStackCheck`**：

   - **栈溢出检查**，详见 [FunctionEntryStackCheck 详解](./function_entry_stack_check.md)
   - **`↳ lazy @-1`**：懒惰解优化点，字节码偏移 -1（函数入口）
   - **3 live vars**：需要恢复 3 个活跃变量（this, arr, closure）

6. **`8/7: Jump b1`**：
   - 无条件跳转到 b1

##### Block b1: 循环准备

```
Block b1
    36: GapMove([stack:-7|t] → [rax|R|t])
    37: ConstantGapMove(n27 → [rcx|R|t])
  4 : GetNamedProperty a0, [0], [0]
   9/9: Jump b2
     │  with gap moves:
     │    - v4/n34:[constant:v-1] → 10: φᴵ r0 [rdx|R|w32]
     │    - v4/n34:[constant:v-1] → 11: φᴵ r1 [rbx|R|w32]
```

**逐行解释**：

1. **`36: GapMove([stack:-7|t] → [rax|R|t])`**：

   - **寄存器移动**：将 `arr`（栈槽位 -7）移动到 rax 寄存器
   - 准备调用 GetNamedProperty

2. **`37: ConstantGapMove(n27 → [rcx|R|t])`**：

   - 将 FeedbackCell 常量移动到 rcx 寄存器

3. **字节码 `4 : GetNamedProperty a0, [0], [0]`**：

   - **操作**：获取 `arr.length`
   - **`[0]`**：常量池索引 0（"length" 字符串）
   - **`[0]`**：反馈槽位索引 0，详见 [FeedbackVector 和反馈槽位详解](./feedback_vector_and_slots.md)
   - **注意**：实际的 CheckMaps 和 LoadTaggedFieldForProperty 在 b2 中

4. **`9/9: Jump b2`**：
   - 跳转到 b2（循环头）
   - **gap moves**：准备 phi 节点的输入值
     - `v4/n34:[constant:v-1]`：常量 0（sum 的初始值）→ phi 节点 10
     - `v4/n34:[constant:v-1]`：常量 0（i 的初始值）→ phi 节点 11

##### Block b2: 循环头（phi 节点 + 循环条件）

```
Block b2 (effects:)
  10/10: φᴵ r0 (n34, n25) → [rdx|R|w32], live range: [10-24]
  11/11: φᴵ r1 (n34, n26) → [rbx|R|w32] (spilled: [stack:0|w32]), live range: [11-21]
         ↱ eager @4 (5 live vars)
  12/12: CheckMaps(0x14200081b835 <Map[16](PACKED_SMI_ELEMENTS)>) [v6/n2:[rax|R|t]]
  13/13: LoadTaggedFieldForProperty(0xc, compressed) [v6/n2:[rax|R|t]] → [rsi|R|t], live range: [13-14]
   8 : TestLessThan r1, [2]
  14/15: UnsafeSmiUntag [v13/n13:[rsi|R|t]] → [rsi|R|w32], live range: [14-17]
  11 : JumpIfFalse [23]
```

**逐行解释**：

   - **输出**：`→ [rdx|R|w32]`，存储在 rdx 寄存器，类型为 w32（word32，32 位整数）

3. **`11/11: φᴵ r1 (n34, n26)`**：

   - **φ 节点**：合并 i 的值
   - **`(n34, n26)`**：初始值 0 vs i+1
   - **输出**：`→ [rbx|R|w32]`，存储在 rbx
   - **`(spilled: [stack:0|w32])`**：可能溢出到栈槽位 0

   - **急切解优化点**，在字节码偏移 4 处
   - 需要恢复 5 个活跃变量

5. **`12/12: CheckMaps(0x14200081b835 <Map[16](PACKED_SMI_ELEMENTS)>)`**：

   - **Map 检查**：确保 arr 是 PACKED_SMI_ELEMENTS 类型的数组
   - **输入**：`[v6/n2:[rax|R|t]]`，arr 在 rax 寄存器
   - 如果 Map 不匹配 → 触发解优化

6. **`13/13: LoadTaggedFieldForProperty(0xc, compressed)`**：

   - **加载 arr.length**
   - **偏移 0xc**：length 字段在 JSArray 对象中的偏移（12 字节）
   - **compressed**：使用指针压缩
   - **输出**：`→ [rsi|R|t]`，length 存入 rsi

   - 测试 `i < arr.length`
   - **`[2]`**：反馈槽位索引

8. **`14/15: UnsafeSmiUntag`**：

   - 将 arr.length 从 Smi（tagged）转换为 int32（untagged）
   - **输入**：`[v13/n13:[rsi|R|t]]`
   - **输出**：`→ [rsi|R|w32]`

9. **字节码 `11 : JumpIfFalse [23]`**：

   - 如果 i >= arr.length，跳出循环（跳转 23 字节）

10. **`15/17: BranchIfInt32Compare(LessThan)`**：
    - **循环条件分支**：`i < arr.length`
    - **输入**：

      - `[v14/n15:[rsi|R|w32]]`：arr.length（rsi）

   - **`[6]`**：反馈槽位索引

    - **`↱ eager @4`**：如果溢出 → 触发解优化

    - **`[0]`**：循环深度
    - **`[7]`**：中断预算减少值（字节码层面）

    - **20**：每次循环减少 20
    - **`[v1/n27:[rcx|R|t]]`**：FeedbackCell 对象（rcx）
    - **`↳ lazy @30`**：懒惰解优化点，字节码偏移 30

13. **`23/29: JumpLoop b2`**：
    - **跳回循环头 b2**
    - 开始下一次迭代
    - **gap moves**（未显示）：将新的 sum 和 i 值传递给 b2 的 phi 节点

##### Block b4: 退出循环

```
Block b4
   24/35: Int32ToNumber [v10/n10:[rdx|R|w32]] → [rax|R|t], live range: [24-26]
   36 : Return

   26/33: Return [v24/n35:[rax|R|t]]
```

**逐行解释**：

1. **`24/35: Int32ToNumber`**：

   - **类型转换**：将 sum 从 int32 转换为 JavaScript Number（Smi 或 HeapNumber）
   - **输入**：`[v10/n10:[rdx|R|w32]]`，sum（rdx，int32）
   - **输出**：`→ [rax|R|t]`，Number 类型的 sum 存入 rax

2. **字节码 `36 : Return`**：

   - 返回指令

3. **`25/32: ReduceInterruptBudgetForReturn(36)`**：

   - **减少返回预算**
   - 用于分层编译决策（函数调用次数统计）

4. **`26/33: Return`**：
   - **返回 sum**
   - **输入**：`[v24/n35:[rax|R|t]]`，sum 在 rax（返回寄存器）

```

迭代 2：

...

```

**关键优化**：

- **无副作用**：`(effects:)` 表示循环体只操作局部变量
- **类型特化**：CheckMaps 确保 arr 是 PACKED_SMI_ELEMENTS
- **边界检查消除**：在循环条件中已经检查 `i < length`
- **整数运算**：sum 和 i 都是 int32，避免 tagged 操作
- **寄存器分配**：sum（rdx）、i（rbx）、arr（rax）都在寄存器中

   | IC 状态 | 含义 | 优化程度 |
   |---------|------|----------|
   | **UNINITIALIZED** | 未初始化，没有反馈 | 无法优化 |
   | **PREMONOMORPHIC** | 预单态，刚开始收集 | 部分优化 |
   | **MONOMORPHIC** | 单态，总是相同的类型/对象 | **最佳优化** ✓ |
   | **POLYMORPHIC** | 多态，2-4 种类型 | 中等优化 |
   | **MEGAMORPHIC** | 超多态，>4 种类型 | 最差优化 |

   **MONOMORPHIC 对优化的意义**：

   - **类型稳定**：每次加载 `Error` 都返回**同一个对象**（全局 Error 构造函数）
   - **可预测**：Maglev 可以假设 `Error` 总是那个特定的构造函数
   - **直接嵌入**：编译器可以将 Error 对象的地址直接嵌入为常量（节点 `n12`）
   - **避免查找**：不需要每次都进行全局对象的属性查找，直接使用缓存的值

   **在这个例子中**：

   ```javascript
   throw new Error("Not a string");
   ```

   - Ignition 执行时，首次加载 `Error` 会记录到 FeedbackVector
   - 记录内容：`Error` 指向的 PropertyCell 和 JSFunction 对象
   - Maglev 编译时，看到 MONOMORPHIC 状态，知道 `Error` 总是同一个函数
   - 直接将 Error 函数对象作为**编译时常量**（`Constant(0x... <JSFunction Error>)`）
   - 生成的代码无需运行时查找，直接使用常量

2. **GapMove([rdi|R|t] → [rdx|R|t])**

   - 复制 Error 构造函数到 `rdx`
   - 这是调用约定的要求

3. **ConstantGapMove(n4 → [rsi|R|t])**

   - 将 ScriptContext 移动到 `rsi`

4. **17/14: 🐢 Construct [...]**

   - 对应 Bytecode: `Construct r1, r2-r2, [2]`
   - 构造 Error 对象，参数为 `"Not a string"`
   - 输入寄存器：`rdi`（Error），`rdx`（Error 副本），`rsi`（context），`v8/n5`（undefined），`v6/n13`（"Not a string"）
   - 输出：`[rax|R|t]`（新创建的 Error 对象）
   - 🐢 表示这是一个"慢路径"操作（需要调用运行时）
   - Deopt: `↳ lazy @18 (4 live vars)`（构造失败时懒反优化）
   - **throw (b4)**：如果构造期间抛出异常，跳转到 b4

5. **18/15: 🐢 Throw(Throw, has_input=1)**

   - 对应 Bytecode: `Throw`
   - 抛出 Error 对象（位于 `rax`）
   - `has_input=1` 表示有输入值（Error 对象）
   - Deopt: `↳ lazy @23 (4 live vars)`
   - **throw (b4)**：抛出后跳转到异常处理器 b4

6. **19/16: Abort(Unexpectedly returned from a throw)**
   - 理论上不应该到达这里（Throw 不会返回）
   - 这是一个保护性检查

##### Block b3: 正常路径（parseInt）

**对应 BytecodeArray**：

```
  24 : LdaGlobal [2], [4]
  27 : Star1
  28 : CallUndefinedReceiver1 r1, a0, [6]
  32 : Return
```

**IR 指令**：

```
Block b3
    45: ConstantGapMove(n17 → [rdi|R|t])
    46: ConstantGapMove(n18 → [rsi|R|t])
    47: ConstantGapMove(n5 → [rdx|R|t])
  20/19: 🐢 CallKnownJSFunction(0x... <SharedFunctionInfo parseInt>, {}) [v7/n17:[rdi|R|t], v1/n18:[rsi|R|t], v8/n5:[rdx|R|t], v8/n5:[rdx|R|t], v12/n2:[rax|R|t]] → [rax|R|t], live range: [20-22]
        ↳ lazy @28 (4 live vars)
        ↳ throw (b4)
    48: ConstantGapMove(n20 → [rcx|R|t])
  21/21: ReduceInterruptBudgetForReturn(32) [v2/n20:[rcx|R|t]]
  22/22: Return [v20/n19:[rax|R|t]]
```

**逐行分析**：

1. **ConstantGapMove(n17 → [rdi|R|t])**

   - 将 `parseInt` 函数移动到 `rdi`
   - 节点 `n17` 是 `Constant(0x... <JSFunction parseInt>)`
   - FeedbackVector：`LoadGlobalNotInsideTypeof MONOMORPHIC`
   - **MONOMORPHIC 状态**：`parseInt` 总是指向同一个全局函数，Maglev 将其作为编译时常量嵌入
   - **详细解释参见**: [inline_cache_deep_dive.md](./inline_cache_deep_dive.md)

2. **ConstantGapMove(n18 → [rsi|R|t])**

   - 将 NativeContext 移动到 `rsi`

3. **ConstantGapMove(n5 → [rdx|R|t])**

   - 将 RootConstant(undefined_value) 移动到 `rdx`

4. **20/19: 🐢 CallKnownJSFunction(0x... <SharedFunctionInfo parseInt>, {})**

   - 对应 Bytecode: `CallUndefinedReceiver1 r1, a0, [6]`
   - 调用 `parseInt(str)`
   - 输入寄存器：
     - `rdi`: parseInt 函数
     - `rsi`: NativeContext
     - `rdx`: undefined（receiver）
     - `rdx`: undefined（重复，调用约定）
     - `rax`: str（参数）
   - 输出：`[rax|R|t]`（parseInt 的返回值）
   - FeedbackVector：`Call MONOMORPHIC`

   **什么是 Call MONOMORPHIC？**

   这是**函数调用的 IC 状态**，表示调用目标的稳定性。**详细解释参见**: [inline_cache_deep_dive.md](./inline_cache_deep_dive.md)


   - **Call**: 函数调用操作的反馈
   - **MONOMORPHIC**: 调用点总是调用**同一个函数**

   **对优化的意义**：

   - **已知目标**：Maglev 知道这里总是调用 `parseInt` 函数
   - **CallKnownJSFunction**：IR 节点名称表明这是"已知函数调用"
     * 相比通用的 `Call` 节点，`CallKnownJSFunction` 更高效
     * 可以跳过一些动态查找和类型检查
     * 可以直接跳转到 parseInt 的入口点
   - **内联可能性**：
     * **Maglev 内联**：有 `MaglevInliner` pass，但策略保守
       - 主要内联小的用户定义函数（字节码大小限制）
       - 对于像 `parseInt` 这样的复杂内建函数，通常不会在 Maglev 阶段内联
     * **TurboFan 内联**：如果函数继续热执行，会被 TurboFan 重新编译
       - TurboFan 的内联能力更强，可以内联更复杂的函数
       - 可能会将 `parseInt` 内联到此处

   **FeedbackVector 详细信息**：

   ```
   - slot #6 Call MONOMORPHIC {
        [6]: [weak] 0x2c5700814ef5 <JSFunction parseInt (sfi = 0x2c570032434d)>
        [7]: 40
     }
   ```

   - `[6]`: 指向被调用函数的弱引用（parseInt JSFunction）
   - `[7]: 40`: 调用计数或其他元数据

   - Deopt: `↳ lazy @28 (4 live vars)`
   - **throw (b4)**：如果 parseInt 抛异常，跳转到 b4

5. **ConstantGapMove(n20 → [rcx|R|t])**

   - 将 FeedbackCell 移动到 `rcx`

6. **21/21: ReduceInterruptBudgetForReturn(32)**

   - 减少中断预算
   - 参数 `32` 是 Bytecode 偏移量

7. **22/22: Return [v20/n19:[rax|R|t]]**
   - 返回 parseInt 的结果

---

##### Block b4: 异常处理器

**对应 BytecodeArray**：

```
  33 : Star1
  34 : CreateCatchContext r1, [3]
  37 : Star0
  38 : LdaTheHole
  39 : SetPendingMessage
  40 : Ldar r0
  42 : PushContext r1
  44 : LdaSmi [-1]
  46 : Return
```

**IR 指令**：

```
Block b4 (exception handler)
    49: ConstantGapMove(n36 → [rax|R|t])
  23/37: SetPendingMessage [v9/n36:[rax|R|t]] → [rcx|R|t]
    50: ConstantGapMove(n20 → [rax|R|t])
  24/39: ReduceInterruptBudgetForReturn(46) [v2/n20:[rax|R|t]]
    51: ConstantGapMove(n38 → [rax|R|t])
  25/40: Return [v10/n38:[rax|R|t]]
```

**逐行分析**：

1. **Block b4 (exception handler)**

   - 这是异常处理器入口
   - 对应 Handler Table: `from 3, to 33 → hdlr 33`

2. **ConstantGapMove(n36 → [rax|R|t])**

   - 将 `the_hole_value` 移动到 `rax`
   - 节点 `n36` 是 `RootConstant(the_hole_value)`

3. **23/37: SetPendingMessage [v9/n36:[rax|R|t]] → [rcx|R|t]**

   - 对应 Bytecode: `SetPendingMessage`
   - 清除待处理的异常消息
   - 将 `the_hole_value` 设置为待处理消息（表示已处理）
   - 返回旧的待处理消息到 `rcx`
   - **详细处理逻辑参见**: [pending_message_deep_dive.md](./pending_message_deep_dive.md)

4. **ConstantGapMove(n20 → [rax|R|t])**

   - 将 FeedbackCell 移动到 `rax`

5. **24/39: ReduceInterruptBudgetForReturn(46)**

   - 减少中断预算
   - 参数 `46` 是 catch 块的 Return 指令偏移量

6. **ConstantGapMove(n38 → [rax|R|t])**

   - 将 Smi 常量 `-1` 移动到 `rax`
   - 节点 `n38` 是 `SmiConstant(-1)`

7. **25/40: Return [v10/n38:[rax|R|t]]**
   - 返回 `-1`（catch 块的返回值）

---

**控制流总结**：

```
第1次调用: parseNumber("123")
  b0 → b1 → b3（"123" 是 string，调用 parseInt，返回 123）

第2次调用: parseNumber(456)
  b0 → b1 → b2（456 不是 string，构造 Error，抛出）→ b4（catch，返回 -1）
```

**关键优化**：

1. **类型反馈良好**：

   - LoadGlobal（Error、parseInt）：MONOMORPHIC
   - Call（Error 构造函数、parseInt）：MONOMORPHIC

2. **两条路径都优化**：

   - 正常路径（b3）：直接调用 parseInt，无额外检查
   - 异常路径（b2 → b4）：内联的异常处理

3. **异常路径标注**：

   - `↳ throw (b4)`：明确标注异常跳转目标

4. **慢路径标记 🐢**：
   - Construct 和 CallKnownJSFunction 标记为慢路径（需要调用运行时）

**与用例 3 的对比**：

| 特性       | 用例 3（safeDivide）  | 用例 4（parseNumber）   |
| ---------- | --------------------- | ----------------------- |
| 类型反馈   | 不足（BinaryOp:None） | 充足（MONOMORPHIC）     |
| 优化结果   | 反优化（2 Block）     | 成功优化（5 Block）     |
| 异常处理   | Handler Table 未使用  | 异常路径完全内联        |
| Block 数量 | 2（b0, b1 → Deopt）   | 5（b0, b1, b2, b3, b4） |

## 三、--print-maglev-graphs：优化阶段分析

`--print-maglev-graphs` 打印每个优化 pass 的 IR 图，帮助理解 Maglev 的优化流程。

### 用例 3: try-catch 的优化阶段

#### 执行命令

```bash
out/x64.debug/d8 --allow-natives-syntax --print-maglev-graphs v8_analyze/maglev_examples/03_try_catch.js 2>&1 > 03_try_catch_phases.txt
```

#### 优化阶段概览

Maglev 编译器的主要优化阶段：

1. **Graph Building**：从字节码构建初始 IR 图
2. **Early Lowering**：早期降低，简化某些操作
3. **Phi Analysis**：分析 phi 节点，优化值合并
4. **Dead Code Elimination**：死代码消除
5. **Common Subexpression Elimination (CSE)**：公共子表达式消除
6. **Loop Optimizations**：循环优化（循环剥离、循环不变量外提等）
7. **Register Allocation**：寄存器分配
8. **Final**：最终优化图

#### 阶段对比示例

**Graph Building（初始图）**：

```
Block b0
  1/1: InitialValue(<this>)
  2/2: InitialValue(a0)
  3/3: InitialValue(a1)
  4/4: FunctionEntryStackCheck
  5/5: Float64Divide [v2, v3]
  6/6: Return [v5]

Block b1 (exception handler)
  7/7: CreateCatchContext
  8/8: Constant(0)
  9/9: Return [v8]
```

**After CSE（公共子表达式消除后）**：

```
Block b0
  1/1: InitialValue(<this>)
  2/2: InitialValue(a0)
  3/3: InitialValue(a1)
  4/4: FunctionEntryStackCheck
  5/5: Float64Divide [v2, v3]  # 已经是最简形式
  6/6: Return [v5]

Block b1 (exception handler)
  7/7: CreateCatchContext
  8/8: SmiConstant(0)          # Constant → SmiConstant（更具体）
  9/9: Return [v8]
```

**After Register Allocation（寄存器分配后）**：

```
Block b0
  1/1: InitialValue(<this>) → [stack:-6|t]
  2/2: InitialValue(a0) → [stack:-7|t]
  3/3: InitialValue(a1) → [stack:-8|t]
  4/4: FunctionEntryStackCheck
  5/5: Float64Divide [v2/n2:[stack:-7|t], v3/n3:[stack:-8|t]] → [xmm0|R|f64]
  6/6: Return [v5/n5:[xmm0|R|f64]]

Block b1 (exception handler)
  7/7: CreateCatchContext
  8/8: SmiConstant(0) → [rax|R|t]
  9/9: Return [v8/n8:[rax|R|t]]
```

**关键变化**：

1. **类型具体化**：Constant → SmiConstant
2. **寄存器分配**：虚拟寄存器 → 物理寄存器（xmm0, rax）
3. **栈位置确定**：参数分配到 stack:-6, -7, -8

#### 优化效果分析

- **死代码消除**：try-catch 的异常路径在正常执行时不会运行，但不能删除（需要保留异常处理能力）
- **CSE**：在 try-catch 中效果有限，因为 try 块内通常操作较少
- **循环优化**：不适用于此用例（无循环）
- **寄存器分配**：Float64Divide 的结果直接分配到 xmm0（浮点返回寄存器）

## 四、--trace-maglev-graph-building：构建过程跟踪

`--trace-maglev-graph-building` 显示从字节码到 IR 的详细转换过程。

### 用例对比：--print-maglev-graph vs --trace-maglev-graph-building

#### 执行命令

```bash
# 最终图
out/x64.debug/d8 --allow-natives-syntax --print-maglev-graph v8_analyze/maglev_examples/01_loop.js 2>&1 > loop_final.txt

# 构建跟踪
out/x64.debug/d8 --allow-natives-syntax --trace-maglev-graph-building v8_analyze/maglev_examples/01_loop.js 2>&1 > loop_trace.txt
```

#### 输出对比

**--print-maglev-graph 输出特点**：

- 显示优化后的最终图
- 包含寄存器分配结果
- Block 结构清晰
- **有**字节码信息（紧凑格式，显示在相关 IR 节点旁边）
- **没有**构建过程细节

**--trace-maglev-graph-building 输出特点**：

- 显示每条字节码的处理过程
- 包含 IR 节点创建细节
- 显示 Block 分割过程
- **有**字节码到 IR 的映射
- **有**控制流构建日志

#### 示例：循环的构建跟踪

**字节码**：

```
4 : GetNamedProperty a0, [0], [0]  # arr.length
8 : TestLessThan r1, [2]           # i < length
11: JumpIfFalse [23]               # 如果假则退出
```

**--trace-maglev-graph-building 输出**：

```
Processing bytecode @4: GetNamedProperty
  Creating CheckMaps node (id=11)
  Creating LoadTaggedFieldForProperty node (id=12)
  Result: v12 (arr.length)

Processing bytecode @8: TestLessThan
  Creating UnsafeSmiUntag node (id=13)
  Input: v12 (arr.length)
  Output: v13 (untagged int32)

Processing bytecode @11: JumpIfFalse
  Creating new merge block b2
  Current block b1 branches to: b2 (true), b6 (false)
  Creating BranchIfInt32Compare node (id=14)
```

**关键信息**：

- **节点创建顺序**：CheckMaps → LoadTaggedField → UnsafeSmiUntag → Branch
- **Block 分割点**：在 JumpIfFalse 处创建新 Block b2
- **值追踪**：v12 (arr.length) → v13 (untagged) → 用于 Branch

#### --trace-maglev-graph-building 的优势

1. **理解优化决策**：

   - 为什么插入 CheckMaps？
   - 为什么需要 UnsafeSmiUntag？
   - Block 是如何分割的？

2. **调试编译问题**：

   - 哪条字节码导致解优化？
   - 哪个 IR 节点生成失败？
   - 控制流构建是否正确？

3. **学习 Maglev 内部机制**：
   - 字节码到 IR 的映射规则
   - 类型推断的过程
   - 控制流图的构建算法

#### 多了哪些信息？

相比 `--print-maglev-graph`，`--trace-maglev-graph-building` 额外提供：

- ✅ **字节码处理日志**：每条字节码的处理过程
- ✅ **节点创建细节**：创建了哪些 IR 节点，为什么
- ✅ **值流追踪**：值如何从一个节点传递到另一个节点
- ✅ **Block 创建过程**：何时何地创建新 Block
- ✅ **类型推断日志**：如何推断值的类型
- ✅ **控制流决策**：为什么创建分支、合并等

#### 少了哪些信息？

`--trace-maglev-graph-building` **不包含**：

- ❌ **寄存器分配结果**：虚拟寄存器还未映射到物理寄存器
- ❌ **优化后的图**：只显示初始构建，没有后续优化 pass
- ❌ **最终 Block 布局**：Block 顺序可能在后续优化中改变
- ❌ **gap moves**：寄存器移动指令在分配阶段才生成

### 符号说明

| 符号          | 含义                            |
| ------------- | ------------------------------- |
| `→`           | 数据流方向                      |
| `↓`           | 控制流继续                      |
| `├─→`         | 分支（true 路径）               |
| `└─→`         | 分支（false 路径）              |
| `↱`           | 急切解优化点（eager deopt）     |
| `↳`           | 懒惰解优化点（lazy deopt）      |
| `[rax\|R\|t]` | 寄存器位置（rax，只读，tagged） |
| `v8/n2`       | 虚拟寄存器 v8，来自节点 n2      |
| `φᴵ`          | Integer phi 节点                |
